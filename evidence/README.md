# Verification results

## Section 1: actual Django Silk capture

[orders-profile.json](orders-profile.json) was generated by:

```sh
docker compose exec web python manage.py profile_orders
```

The run used Django 5.2.18, django-silk, PostgreSQL, and 250 orders with two items per
order. It made authenticated requests to both views and checked that their JSON
responses were identical.

| Measurement | Broken view | Fixed view |
| --- | ---: | ---: |
| Queries involving the order models | 1,001 | 2 |
| Total queries, including session/user lookup | 1,003 | 4 |
| Request duration recorded by Silk | 6,247.22 ms | 45.44 ms |
| Sum of recorded SQL durations | 739.57 ms | 7.47 ms |

These are local measurements with profiling enabled, not a reproduction of the
brief's exact 30-second timeout. Silk itself adds overhead, particularly when
collecting stack traces for 1,003 queries. Query counts and equal output are the
main evidence; wall-clock timings vary across machines.

The JSON includes request IDs and sample SQL. The corresponding full query lists
are available in the local Silk UI after running the command. A fresh clone will
create its own request IDs and timings.

## Section 2: queue verification

The clean full-suite command was `docker compose run --rm tests`.
Result: **27 passed in 214.78 seconds**, with no skipped tests or failures.
The run used a fresh PostgreSQL test database, real Redis, and Linux prefork workers.
The [JUnit report](test-results.xml) records the individual test cases and durations.

The [500-job report](queue-500.json) records:

| Check | Result |
| --- | ---: |
| Jobs submitted / sent | 500 / 500 |
| Unique provider receipts | 500 |
| Provider attempts, including the intentional failure | 501 |
| Queue test duration, including the initial 60-second hold | 184.01 seconds |
| Smallest span containing 201 consecutive admissions | 60.000587 seconds |

Every group of 201 consecutive admissions spanned at least 60 seconds, so no
rolling 60-second window exceeded 200 admissions. The JSON includes all 501 Redis
timestamps for checking this independently. The deliberately failed job had two
attempts, a recorded two-second minimum backoff, and one receipt.

Both actual SIGKILL cases passed: killing one prefork child, and killing the whole
worker after provider acceptance. Each recovered to `sent` with two task attempts
but only one provider receipt. The crash tests use shorter lock/visibility timeouts;
the 500-job test keeps the normal application settings.

Django system checks, migration consistency, Ruff linting, and formatting also
passed. New runs write to `artifacts/`; these checked-in files preserve this run.
